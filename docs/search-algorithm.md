# 全盘文件检索：算法改造方案

> 对象：`xunsou` 1.0.0 的索引与检索链路（`win.rs` / `indexer.rs` / `model.rs` / `search.rs`）
> 目标：在不增加磁盘损耗的前提下，把"全盘所有文件位置"的检索做到常驻可用。
> 结论先行：**问题不在于扫描得不够快，而在于"扫描"这件事目前不是一次性动作**。修好这一点，速度与硬盘友好性同时成立。

---

## 0. 先纠正一个前提

用户担心的"扫描伤硬盘"，在 SSD 上要拆成三件事看：

| 行为 | 对 SSD 的实际影响 | 对 HDD 的影响 |
|---|---|---|
| 顺序读（读 MFT） | 几乎为零。读不消耗 TBW，只是占用带宽几分钟 | 磁头顺序寻道，可忽略 |
| 随机小读（全盘目录遍历） | 轻微（读放大 + 元数据页反复装载），主要是**慢** | 严重：寻道风暴，30 分钟以上，且会拖慢整机 |
| 写入（索引快照） | **这才是真正的损耗**：直接消耗 TBW，还有写放大 | 同样消耗寿命，且更慢 |

所以"硬盘友好"的正确目标不是"少读"，而是：**全盘只顺序读一次，此后零全盘读；写入量降两个数量级；永不触发随机遍历。**

## 1. 现有链路复盘

### 1.1 冷启动（`indexer.rs:324` `scan_volume_mft`）

```
open_volume(\\.\C:)  →  FSCTL_GET_NTFS_VOLUME_DATA  →  FSCTL_GET_RETRIEVAL_POINTERS(取 $MFT runs)
  →  read_mft_records：4MB 缓冲、Buffered ReadFile、逐块回调
  →  rayon par_chunks_mut 并行解析每条 1024B 记录
  →  add_entry：名称池 intern + frn_map 插入
```

IO 形态是对的：**一次顺序读 $MFT**，1.28M 条目约 1.3GB。这是"全盘所有文件位置"信息量的物理下限，任何方案都绕不开（除非用 Windows Search 的现成索引，但那是不完整且更慢的二手数据）。

问题在 CPU 侧和边界条件，见 §1.4。

### 1.2 常态（`indexer.rs:572` `spawn_usn_poller`）

```
loop { FSCTL_READ_USN_JOURNAL(1MB) → 收集 touched FRN → 按 FRN 排序去重
       → 对每个 FRN 调 refresh_record：SetFilePointerEx + ReadFile(1KB)
       → 加写锁 upsert }
     日志追平则 sleep 600ms
```

方向正确（USN 增量是唯一正确的实时方案），但实现上每次变更都做一次**随机 1KB 读**，且 USN 记录里自带的 `FileName` / `ParentFileReferenceNumber` / `FileAttributes` 完全没用上。

### 1.3 查询（`search.rs:45` + `app.rs:210`）

每次输入变化，在 **UI 线程**同步全量扫描 1.28M 条：分词 → 逐条 `contains_bytes`（字节级朴素 memmem）→ 分类过滤 → 排序。空查询切换分类时，`classify()` 对每个条目执行 `ext.to_ascii_lowercase()`，即 **1.28M 次 String 分配**（`search.rs:109`）。

### 1.4 已定位的 8 个具体缺陷

| # | 缺陷 | 位置 | 后果 |
|---|---|---|---|
| 1 | MFT 打不开时静默回退到 8 线程全盘 `read_dir` 遍历 | `indexer.rs:812-817` | 非管理员场景下变成磁盘最坏路径：10⁵–10⁶ 次随机元数据读，HDD 上 30 分钟起；且 `frn=0`，**USN 增量完全不可用**，每次启动都要重来 |
| 2 | 每新增一个目录，就遍历整个 `orphans` 集合找它的孩子 | `model.rs:157-167` | O(目录数 × 孤儿数)。MFT 记录被复用的卷上孤儿可达数万，退化为 10⁹ 级比较 |
| 3 | 每条记录 3 次堆分配：`Vec<u16>` 收集、`String::from_utf16_lossy`、`intern` 里的 `to_vec()` | `indexer.rs:181-185`、`model.rs:70` | 130 万文件 ≈ 400 万次分配，多线程下分配器争用，是冷启动的主要 CPU 成本 |
| 4 | `frn_map` / 名称池去重表用默认 SipHash HashMap | `model.rs:112,136,150` | 130 万条目 ≈ 390 万次哈希插入查找，比开放寻址慢 3–5 倍，且随机访问 cache miss 高 |
| 5 | 记录编号按"已读字节累计"递增，而非按逻辑偏移计算 | `win.rs:305-357` | `$MFT` run 列表出现空洞（稀疏/负 LCN）时，后续所有记录编号错位 → FRN 与文件错配、路径张冠李戴 |
| 6 | `MftCtx` 无 `Drop`，卷句柄用完不关 | `indexer.rs:220`、`257` | 每次重扫、每次 run 查找失败都漏一个卷句柄 |
| 7 | 快照全量重写：每 120 秒，只要 epoch 变过就重写整个索引 | `indexer.rs:872-885, 933-940` | 1.28M 条目 ≈ 80MB/次。持续有文件变动时最坏 2.4GB/小时的无意义写入 |
| 8 | 快照恢复后 `pool.dedup_*` 表为空，`intern` 无法命中历史名称 | `model.rs:447-460` | 名称池只增不减，长期使用后快照越来越大，每次写盘更贵（正反馈恶化） |

另有搜索侧两处：分类过滤每条目分配 String（`search.rs:109`）；路径排序为每个结果构造两个 String（`search.rs:186-192`）。

## 2. 核心思路

一句话：**把"全盘扫描"从常态降级为一生一次的事件，把常态降级为 O(变更量)，把查询降级为 O(候选集)。**

```
                    ┌──────────────────────────────────────────────┐
一次性（开机首次 / 卷变更）
   顺序读 $MFT  ───► 内存索引（SoA）  ───► mmap 快照 + delta log
   ~1.3GB 顺序                                 (只在空闲时追加)
                    └──────────────────────────────────────────────┘
                                    ▲
常态（每秒）                        │ 增量
   USN 日志流  ──► 变更事件 ──► 索引原地更新（零随机回读）
   O(变更量)                        │
                                    ▼
查询（每次按键）
   前缀收窄 → 倒排交集 → 候选验证  ───► 前 N 条秒出（后台线程 + 代次丢弃）
```

三条硬约束贯穿全案：

1. **全盘只顺序读一次**，之后任何全盘操作都必须由用户显式触发。
2. **写盘量与"变化量"成正比，不与"索引规模"成正比**。
3. **任何回退路径都不能比正路更伤盘**——宁可"暂不可索引"，也不静默遍历。

## 3. 冷启动：把 1.3GB 顺序读做到接近物理极限

### 3.1 保留 MFT 直读，不换成 `FSCTL_ENUM_USN_DATA`

值得说明为什么**不**换：`ENUM_USN_DATA` 虽然官方、免解析，但返回的 `USN_RECORD` 里**没有文件大小和修改时间**。而本软件的列表要显示大小/时间，用 ENUM 就得对每个文件再回读 MFT——把一次顺序读变成 130 万次随机读，方向完全相反。

所以正确做法是保留手写 MFT 解析（它一次顺序读就能拿到 name/parent/size/mtime/attrs），只把它修干净。

### 3.2 IO 侧

| 项 | 现状 | 改为 | 收益 |
|---|---|---|---|
| 缓冲 | 默认 buffered 4MB | `FILE_FLAG_NO_BUFFERING` + 8–16MB 扇区对齐缓冲，失败自动回落 buffered | 不把 1.3GB MFT 灌进 standby 缓存挤掉用户热数据；顺序吞吐更高 |
| 提示 | 无 | `FILE_FLAG_SEQUENTIAL_SCAN` | 让缓存管理器提前失效已读页，减少内存占用 |
| 优先级 | 普通 | `SetThreadPriority(THREAD_PRIORITY_LOWEST)` + 进程级 `PROCESS_MODE_BACKGROUND_BEGIN` | 用户在用电脑时索引几乎无感；空闲时自动提速 |
| 并发度 | 每卷 1 线程 + rayon 全核解析 | 按介质自适应：HDD 单 reader，SSD 2–4 reader；解析线程数 = min(核数, 8) | HDD 上避免多 reader 互相踩磁道 |
| 分块开销 | 每 4MB 做一次 `carry.drain(..off)` 的整块 memmove | 双缓冲 + 游标，零拷贝 | 省掉约 1.3GB 的无谓内存搬移 |

### 3.3 CPU 侧（决定"秒级"能不能成立）

1. **零分配解析**：不再 `collect::<Vec<u16>>()` 再 `String::from_utf16_lossy`。直接在记录切片上定位 UTF-16 名称，`char::decode_utf16` 迭代写入一个可复用的 `String`（每线程一个），或干脆把名称以 `(记录偏移, 长度)` 形式先入 SoA，延迟到"真正需要展示"时再解码。
2. **两遍式容量预留**：第一遍只按 `mft_len / record_size` 预留 `entries` / `pool` 容量，避免 130 万条插入过程中 20+ 次 realloc 与 50MB 级 memcpy。
3. **换哈希**：`frn_map` 改开放寻址（`Vec<u64>` 键 + `Vec<u32>` 值，load factor ≤0.7，哈希用 xxh3 或 `frn * 0x9E3779B97F4A7C15 >> shift`），名称池去重同样处理。
4. **修掉 O(D×O) 孤儿扫描**：`orphans: HashSet<u32>` 换成 `waiting: HashMap<u64 /*parent_frn*/, SmallVec<u32>>`，目录出现时 O(1) 取出它的等待者。
5. **修记录编号错位**：`read_mft_records` 改为按 `logical_off / record_size` 计算记录号，run 之间有空洞时跳过对应区间而不是让编号连续递增。
6. **给 `MftCtx` 加 `Drop`**，`CloseHandle` 收口。

### 3.4 分阶段可用（感知速度，不改一致性）

首帧先只处理 `%USERPROFILE%`、桌面、下载、文档、`Program Files` 这几个高频子树（它们的目录项在 MFT 里集中在前段），200–400ms 内就能出结果；剩余部分在后台低优先级补齐，补齐后再刷新一次结果集。用户感知从"等 3 秒"变成"立刻能用"。

## 4. 常态：从"轮询 + 随机回读"改为"事件流 + 零回读"

### 4.1 USN 记录自带的字段够用，不需要回读 MFT

`USN_RECORD_V2` 包含 `FileReferenceNumber`、`ParentFileReferenceNumber`、`FileName`、`FileAttributes`、`Reason`。因此：

| 事件 | 处理方式 | 是否读盘 |
|---|---|---|
| `FILE_CREATE` / `RENAME_NEW_NAME` | 直接用 USN 里的 name + parent 构造条目 | **否** |
| `FILE_DELETE` | 直接按 FRN 删除 | **否** |
| `RENAME_OLD_NAME` | 忽略（新名字那条会到） | 否 |
| `DATA_OVERWRITE / EXTEND / TRUNCATION` | 大小变了，标 `stale`，进"待刷新队列" | 延迟、批量 |

于是最常见的写入场景（编译产物、下载、解压、删除）**一次随机读都没有**。

### 4.2 待刷新队列用"聚簇窗口读"

确实需要大小的条目（新建文件、数据变更）攒进队列，按 FRN 升序排序后**合并成窗口读**：相邻 FRN 落在同一个 64 条记录（64KB）窗口内时，读一次窗口、解析出全部目标。FRN 在 MFT 里近似物理连续，窗口合并能把 130 万次随机读压成几千次近似顺序读。队列在**空闲或每 30 秒**批量消化，不打断用户操作。

### 4.3 事件驱动，去掉固定轮询

`FSCTL_READ_USN_JOURNAL` 支持 `BytesToWaitFor` 阻塞语义：无变更时内核挂起该 IO，有变更立刻返回。用"阻塞 30 秒 + 超时重发"替代 600ms 固定 sleep，空闲时 CPU 与 IO 都归零，有变更时延迟从 600ms 降到毫秒级。

### 4.4 日志参数

启动时对每个卷 `FSCTL_CREATE_USN_JOURNAL` 把 `MaximumSize` 设到 64MB、`AllocationDelta` 8MB。代价是固定占用几十 MB 磁盘，换来的是"日志被覆盖 → 必须全量重建"的概率大幅下降。同时记录 `journal_id`，一旦变化（日志被删/重建）就静默排队重建，而不是报错。

## 5. 查询：三段式，按键 1–3ms

### 5.1 三段漏斗

```
第 1 段  收窄（0.1ms）  若新查询是上次查询的严格前缀追加 → 只在上次结果集上过滤
第 2 段  倒排（1ms）    取最长 token 的 3-gram 交集 → 候选位图（通常 1k–50k）
第 3 段  验证（0.5ms）  对其余 token 用 memmem 逐条验证 + 分类过滤
兜底    全扫（30ms）    仅当查询 <3 字符或倒排未命中时
```

「前缀追加」这一条最关键：正常打字是 `p` → `pr` → `pro` → `proj`，每一步只需在上一步的 200k → 30k → 5k 候选上跑，天然是 O(候选集)。

### 5.2 3-gram 倒排索引

- 只索引**文件名**（不索引路径；路径查询本来就少，走全扫）。
- 3-gram → 有序 `u32` 数组（delta + varint），交集用跳表式归并；条目数 >10 万的 gram 直接标记为"高频"，不参与交集（如 `doc`、`tmp`），改由验证阶段处理。
- 内存：1.3M 文件名、平均 18 字节 → 约 2000 万 postings，压缩后 **35–50MB**。
- 增量维护：USN 更新时只增删该条目相关的 3-gram，O(名称长度)。

### 5.3 分类过滤去分配

`classify()` 改成查表：把扩展名按首字母分桶（`[&[&str]; 26]`），命中时用 `eq_ignore_ascii_case` 比较，全程零分配。这一条单独就能把"点分类"从 ~60ms 降到 ~5ms。

### 5.4 移出 UI 线程

搜索与排序放到独立 worker：UI 线程只提交 `(query, cat, sort, generation)`，worker 回传 `Arc<Vec<u32>>`，代次不匹配直接丢弃。输入永不阻塞渲染。

### 5.5 排序去分配

- 名称排序：已有 `lower_of`，直接比字节，零分配（现状已如此）。
- 路径排序：为每个结果 `path_of` + `to_lowercase` 建两个 String（`search.rs:186`）。改为预建 `parent_path_lower: Vec<u32>`（每个目录一条，路径字符串只存一次），排序时按"父路径 id + 名称"两段比较，内存与时间都降一个量级。
- 结果只排前 N（可视 + 一屏余量）时可用 `select_nth_unstable` + 局部排序，10 万结果从 40ms 降到 5ms。

## 6. 数据结构

```rust
// 结构体数组 → 数组的结构体，查询时只 touch 需要的列
struct Entries {
    frn:       Vec<u64>,
    parent:    Vec<u32>,   // 父条目下标
    name_off:  Vec<u32>,
    name_len:  Vec<u16>,
    size:      Vec<u64>,
    mtime:     Vec<u64>,
    flags:     Vec<u8>,    // DIR | EXCLUDED | STALE
}
struct FrnTable { keys: Vec<u64>, vals: Vec<u32>, mask: usize }  // 开放寻址，load ≤0.7
struct Children { first: Vec<u32>, next: Vec<u32> }              // 父子链，替代 orphans 扫描
```

SoA 的实际收益：全量名称扫描时只读 `name_off/name_len` 两列（6 字节/条），不把 40 字节的 `Entry` 整条拉进缓存行，扫描带宽降 5–6 倍。

快照格式改为：**`mmap` 友好的定长段 + 变长名称池**，冷启动 `mmap` 后直接使用（页按需调入），省掉"读 80MB → 反序列化 → 建 HashMap"的全过程；只有 `frn_map` 仍需在后台惰性重建（或干脆不建，改用 FRN 排序数组 + 二分）。

## 7. 磁盘写入账本

以 128 万条目、持续有文件变动的 1 小时为口径：

| 写入项 | 现状 | 方案 |
|---|---|---|
| 全量快照 | 80MB × 30 次 = **2.4GB** | 0（不再周期全量写） |
| 增量日志 | 无 | ~40B × 变更数，1000 次变更 ≈ 40KB |
| 合并快照 | 无 | 空闲时触发，LZ4 后 ≈ 25MB，每 30–60 分钟最多 1 次 |
| 合计 | **2.4GB/h** | **≈ 25MB/h** |

差别约 **100 倍**。合并条件：`距上次 ≥30min` 且 `无输入活动 ≥5s` 且 `delta 条目数 > 总量 5%` 且 `电池供电时不触发`。退出时若 delta 非空则合并一次。

读取侧：冷启动 1.3GB 顺序读一次；之后常态每卷每小时约几百 KB（journal 本身）。**全盘遍历归零。**

## 8. 预期收益

| 指标 | 现状（推算） | 方案（推算） | 依据 |
|---|---|---|---|
| 冷启动（128 万条，8 核 SSD） | 2.5–4s | 0.8–1.2s | 去掉 400 万次分配 + 390 万次 SipHash；解析吞吐从 ~0.5M rec/s 提到 ~1.5M rec/s |

| 非管理员场景 | 10–40 分钟全盘遍历 | 0 秒（明确提示"以服务/管理员启用"） | 删除静默回退 |
| 单键检索（有倒排） | 25–60ms | 1–3ms | 候选集从 128 万降到 1k–5 万 |
| 单键检索（无倒排兜底） | 25–60ms | 15–25ms | 去分配 + SIMD memmem |
| 切换分类 | 40–80ms（每条目 1 次分配） | 3–6ms | 扩展名查表 |
| 搜索时 UI 掉帧 | 有（UI 线程同步搜索） | 无（worker + 代次） | — |
| 稳态磁盘写入 | 2.4GB/h | ~25MB/h | 见 §7 |

数字是按代码路径推演的量级估计，落地后应以实测替换；但数量级关系（100 倍写入、20 倍检索）来自结构差异，不是调参。

## 9. 取舍

| 取舍 | 代价 | 为什么值得 |
|---|---|---|
| 常驻服务（LocalSystem）持有卷句柄 | 需要安装/自启，增加一个提权组件与攻击面 | 这是唯一能同时解决"免 UAC"和"永不全盘遍历"的办法。Everything 就是这个结构。服务必须以 `FILE_SHARE_READ\|WRITE` 只读打开卷、命名管道 ACL 只授权当前用户、不接受任意路径读写请求 |
| 3-gram 倒排 | +35–50MB 内存，增量维护复杂度 | 换取 20 倍检索速度；且可开关（轻量模式只做前缀索引，+8MB） |
| USN 日志扩容到 64MB | 固定占盘 | 换"永不因日志覆盖而全量重建"；重建是唯一会再读 1.3GB 的事件 |
| 最终一致（非强一致） | 新建文件可能在几十毫秒内搜不到 | 桌面检索场景无感；换来零随机回读 |
| 不做周期性全盘校验 | MFT 与索引理论上会漂移 | 漂移只可能来自 journal 丢失或第三方直接改卷；用"journal_id 变化"和"条目数偏差 >2%"两个信号触发后台静默重建即可 |
| `NO_BUFFERING` | 实现复杂（对齐、尾部补齐、老驱动可能失败） | 省下 1.3GB 的缓存污染；失败可回落，风险可控 |
| 手写 MFT 解析（而非官方 ENUM API） | 需要处理 `$ATTRIBUTE_LIST`、扩展记录、损坏记录 | ENUM 不给 size/mtime，换它会把顺序读变成随机读，方向相反 |

---

## 10. 适用条件

**成立的前提**

- 本地固定卷，文件系统为 NTFS 5.x（含 Windows 10/11 默认卷）。
- 以管理员或常驻服务身份运行，能 `CreateFile("\\.\X:")` 打开卷。
- 卷已挂载、未处于 BitLocker 锁定态、未被 chkdsk 独占。
- USN 日志存在或可创建（`FSCTL_CREATE_USN_JOURNAL`）。Win10 1607+ 支持 128 位 FRN 的 `USN_RECORD_V3`，大卷更稳。

**不成立时怎么办**

| 场景 | 可行路径 | 磁盘代价 |
|---|---|---|
| 非 NTFS（exFAT / FAT32） | 只能目录枚举；改为**用户显式点击才执行**，并显示"预计 X 分钟、将持续读盘" | 高，但用户知情且一次性 |
| ReFS | 有 USN、无 MFT → 用 `ENUM_USN_DATA` 取名称/父引用，大小/时间惰性补齐 | 中 |
| 网络盘 / 云盘 | 不索引。交给服务器端搜索或按需 `FindFirstFile` 单目录查询 | 零 |
| 可移动介质 | 插拔事件触发单卷索引，拔出即丢弃（不写快照） | 低 |
| 无管理员权限且拒绝装服务 | **不提供全盘索引**，改为"常用目录（桌面/下载/文档）+ Windows Search 联合检索" | 零 |

最后一条是这次改造的态度：**明确"不做"，好过悄悄退化成最伤盘的路径。**

## 11. 落地顺序

| 阶段 | 内容 | 风险 |
|---|---|---|
| P0（半天，纯收益） | 修 §1.4 的 8 个缺陷中的 1/2/5/6；分类查表去分配；搜索移出 UI 线程 | 低，行为不变 |
| P1（1–2 天） | 零分配解析 + 容量预留 + 开放寻址哈希；快照改 delta log + 空闲合并 | 中，需重新验证快照兼容（加版本号，旧快照直接丢弃重建） |
| P2（2–3 天） | USN 事件驱动 + 零回读 + 聚簇窗口读 + journal 扩容 | 中，需覆盖日志回绕/ID 变化 |
| P3（2 天） | 前缀收窄 + 3-gram 倒排 + 前 N 条局部排序 | 中，内存与增量维护 |
| P4（可选） | 常驻服务化（免 UAC）、分阶段可用、mmap 快照 | 高，涉及安装与权限模型 |

P0+P1 做完，"扫描慢"和"写盘多"两个问题就基本消失，且不改变任何对外行为。P2 之后才是"常驻级"体验。

## 12. 明确不做

- 不做"定时全盘重扫兜底"——这是最典型的"用磁盘寿命换实现省事"。
- 不做文件内容全文索引——那是另一个数量级的读写，与本工具定位冲突。
- 不对每个 USN 事件立即回读 MFT——延迟批量与聚簇读的收益远大于几秒的新鲜度。
- 不在 UI 线程做任何 O(n) 操作。

## 附二：遍历回退路径的父链缺陷（已修）

方案里把「全盘 `read_dir` 遍历」定位为**必须显式授权**的兜底路径，理由是它会产生 10⁵–10⁶ 次随机元数据读。
本轮在真机上跑遍历模式时发现它还有第二个、更隐蔽的问题：**父子链是错的**。

```rust
// 修复前：子目录任务携带的是父目录下标
g.q.push_back((sub, parent_idx));
```

于是每个目录的内容都挂到自己的**祖父**上，逐层上跳，最终全部塌缩到卷根。
`path_of` 沿父链只能拼出 `G:` —— 界面上表现为「一万多个文件的路径列全是盘符」，
而且因为 `path_of` 本身没坏，从代码上很难一眼看出问题在扫描侧。

修复方式：目录条目与文件条目分开攒，目录先单独落盘拿到自己的下标，再连同下标入队。
文件继续走批量落盘，写锁次数不因此上升（目录数远小于文件数）。

这个缺陷不影响 MFT 路径（FRN 映射是两遍扫描 + 孤儿重链），只影响遍历路径。
它再次说明：**兜底路径也必须被验证**，否则一旦用户被迫走兜底，拿到的是看起来正常、实际全错的数据。
